## 0. ผลการดำเนินการ (2026-10-27)

**ทีมตัดสินใจ (ตอบคำถามในหัวข้อ 10):** (1) เครื่องอ้างอิง = iPhone 12 Pro (2) แท็บเล็ต/จอใหญ่คงขนาดเดิม (`S_MAX = 1`) (3) G13 ใช้**วิธี 2** — ย้ายโลกเป็นหน่วยเวที (4) ทำ G20 และ G20K พร้อมกัน

**ที่ต่างจากแผนเดิม (เนื้อหาหัวข้อ 6–8 ด้านล่างเป็นบันทึกการออกแบบ ให้ยึดหัวข้อนี้เมื่อขัดกัน):**
- **ขนาดอ้างอิง = root ของเกมบน iPhone 12 Pro = 388 × 844** (ไม่ใช่ 390) เพราะ `#root-container` มีเส้นขอบซ้าย-ขวา 1px — e2e จับได้ว่าถ้าใช้ 390 จอนี้จะได้ `s = 0.995` แทน 1 และ**ใช้ขนาดเดียวกันทุกเกม** วัดจาก root ทั้งเกม (รวมหัวการ์ด) ไม่ใช่พื้นที่เล่นหลังหักหัวการ์ด — เลี่ยงวงวน "หัวการ์ดย่อ → พื้นที่เล่นเปลี่ยน → `s` เปลี่ยน"
- **G13 วิธี 2 แบบเบาที่สุด:** โลก = ขนาด canvas ÷ `s` (`world.width/height` เป็นหน่วยเวที) วาดด้วย `setTransform(dpr × s)` ค่าคงที่/ฟิสิกส์/การรับ/กล้อง**ไม่ต้องแก้สักตัว** เพราะเดิมก็เป็นหน่วยเดียวกันอยู่แล้ว จอเตี้ยจึงได้โลกที่กว้าง/สูงขึ้นในหน่วยเวที (ไม่ได้ล็อกสนามกว้างคงที่แบบ G20 — จะมีกำแพงล่องหนกลางจอ)
- **ตัวแปร CSS ตั้งแบบ imperative** ใน callback ref (`el.style.setProperty('--gp-s', …)`) — inline ชนะ media query ของ `.gp-compact` ไม่ต้องแก้ `globals.css`; หน้าแนะนำเกม (`GameIntro`) คงแบบขั้นบันไดเดิม

## 1. สรุปสั้น

**ทำได้ และควรทำ** — ระบบที่แนะนำคือ **"ความละเอียดออกแบบ (design resolution) + ตัวคูณสเกลเดียวต่อเกม"**: แต่ละเกมกำหนดขนาดพื้นที่เล่นอ้างอิงไว้หนึ่งค่า (เช่น 390 × 700) แล้วตอนเล่น วัดพื้นที่เล่นจริงบนเครื่อง คำนวณตัวคูณ `s` และย่อทุกองค์ประกอบในเกมด้วย `s` เดียวกัน เกมจึงมีสัดส่วนเท่ากันทุกเครื่อง ไม่ว่าจอจะกว้าง 320 หรือ 430 px

**ต้นเหตุจริงไม่ใช่ขนาดจอจริง (นิ้ว) แต่เป็นขนาด viewport (หน่วย CSS px) ที่ต่างกันมาก** ระหว่างตัวจำลองกับเครื่องจริง (ข้อมูลจาก log ภาคสนามจริงใน [หัวข้อ 3](#3-หลักฐาน-ขนาดจอจริงจาก-log-ภาคสนาม)):

| | ตัวจำลองที่ทีมใช้ทดสอบ (โดยทั่วไป) | มือถือจริงของผู้เรียน (median) |
|---|---|---|
| ขนาด viewport | 390 × 844 หรือ 412 × 915 | **384 × 666** (ใน LINE: สูง **636**) |
| ความกว้าง 320 px (ตั้ง "ขนาดการแสดงผล"/Display Zoom ให้ใหญ่) | ไม่มี | **11%** ของเครื่อง |

เกมที่วาดองค์ประกอบเป็นขนาด px ตายตัว (ไม่สนว่าพื้นที่เล่นเหลือเท่าไหร่) จึงกินพื้นที่บนเครื่องจริงมากกว่าบนตัวจำลอง 1.3–1.7 เท่า **ตัวที่เป็นปัญหาหนักที่สุดคือ G13** (กรวยกับลูกไอติมเป็น px คงที่) ส่วน **G20/G20K ทำระบบนี้อยู่แล้ว** (stage 540 × 960 + `fitStage`) และใช้เป็นต้นแบบได้เลย

## 2. ทำไมตัวจำลองดูปกติ แต่เครื่องจริงใหญ่เกิน

เบราว์เซอร์วาดทุกอย่างเป็น **CSS px** ไม่ใช่ pixel จริงของจอ จำนวน CSS px ที่เครื่องหนึ่งมีให้ (viewport) ขึ้นกับหลายปัจจัยที่ตัวจำลองไม่ได้จำลอง:

1. **แถบของแอป LINE / เบราว์เซอร์กินความสูง** — ตัวจำลองใน DevTools ให้ความสูงเต็มเครื่อง (เช่น 844) แต่ใน LINE in-app browser มีแถบชื่อเว็บด้านบน + แถบเครื่องมือด้านล่าง เหลือ ~610–690 px (ผู้เรียน 71% เปิดผ่าน LINE)
2. **ผู้สูงอายุมักตั้ง "ขนาดการแสดงผล" (Android Display size) หรือ "Display Zoom" (iPhone) ให้ใหญ่** — การตั้งนี้ทำให้ viewport แคบลง เช่น เครื่องเดิมรายงาน 412 → 360 → 320 px ทุกอย่างที่เป็น px ตายตัวจึงดูใหญ่ขึ้นตามสัดส่วน ข้อมูลจริงพบความกว้าง 320 px ถึง 11% ของเครื่อง ซึ่งแทบไม่มีมือถือรุ่นปัจจุบันที่จอกว้าง 320 จริง
3. **(สมมติฐาน ต้องวัด)** LINE บน Android เป็น WebView ที่อาจคูณขนาดตัวอักษรตาม "ขนาดตัวอักษร" ของระบบ (`textZoom`) ทับ `text-size-adjust: 100%` ที่เราตั้งไว้ใน `globals.css` — ถ้าจริง ข้อความ/อีโมจิใน DOM (เช่นผลไม้ของ G19, ตัวเลข HUD) จะใหญ่เกินด้วย แต่ภาพที่วาดบน canvas จะไม่โดน ข้อ [S0](#s0-วัดผลบนเครื่องจริงก่อน-ทำก่อนทุกข้อ) มีวิธีวัด

ผลรวมคือ **พื้นที่เล่นบนเครื่องจริงเล็กกว่าตัวจำลอง แต่ตัวละครยังขนาด px เท่าเดิม** → ตัวละครกินสัดส่วนจอมากขึ้น จนบางเครื่องเล่นไม่ได้

> หมายเหตุ: ปัญหานี้ไม่ได้มาจาก `devicePixelRatio` (ความคมชัด) — ค่านี้ทุกเกมจัดการถูกแล้ว (ใช้ตั้งขนาด buffer ของ canvas เท่านั้น ไม่กระทบขนาดที่ตาเห็น)

## 3. หลักฐาน: ขนาดจอจริงจาก log ภาคสนาม

ทุก event ที่ `loggingService` ส่งมี `screenSize = innerWidth × innerHeight` อยู่แล้ว ([`src/services/loggingService.ts:47`](../../src/services/loggingService.ts)) — วิเคราะห์จาก `docs/analytics/{aug07,aug18,aug19,sep19}/action_logs.csv` เฉพาะ session มือถือแนวตั้ง (กว้าง ≤ 500 px), ใช้ค่าที่เล็กที่สุดของแต่ละ session:

| | จำนวน |
|---|---|
| session มือถือ | 239 (เปิดผ่าน LINE 170 = 71%) |

| เปอร์เซ็นไทล์ | กว้าง (px) | สูง (px) |
|---|---|---|
| p05 | 320 | 531 |
| p10 | 320 | 579 |
| p25 | 360 | 613 |
| **p50 (median)** | **384** | **666** |
| p75 | 393 | 720 |
| p90 | 428 | 775 |

- กว้าง ≤ 360 px: **98 เครื่อง (41%)** | กว้าง < 340 px: 27 เครื่อง (11%)
- สูง ≤ 660 px: **115 เครื่อง (48%)** | สูง < 600 px: 35 เครื่อง (15%)
- median ความสูงเฉพาะใน LINE: **636 px**
- ขนาดที่พบบ่อย: `360×612–647` (Android/LINE), `384×640–673` (Android/LINE), `390×669` (iPhone/LINE), `414×720` (iPhone/LINE), `320×535` (Android/LINE ตั้งขนาดการแสดงผลใหญ่)

**ข้อสรุป:** ควรทดสอบและออกแบบที่ **360 × 612** เป็นค่า "เครื่องทั่วไป" และ **320 × 535** เป็นค่า "เครื่องเล็กสุดที่ต้องเล่นได้" ไม่ใช่ 390 × 844

## 5. ทางเลือกที่พิจารณา

### ทางเลือก A — เปลี่ยน `<meta name="viewport" content="width=…">` ต่อหน้าเกม (เปลี่ยน "ความละเอียด" ของทั้งหน้า) ❌ ไม่แนะนำ

ตั้ง viewport เป็นความกว้างตายตัว (เช่น `width=412`) ให้เบราว์เซอร์ย่อทั้งหน้าเอง — ตรงกับคำว่า "เปลี่ยนความละเอียด" ที่สุด แต่:
- แก้ได้แค่ความกว้าง ไม่ได้แก้ปัญหาความสูงที่ LINE กินไป (ต้นเหตุหลักของ G13)
- iOS Safari/WebView ไม่ได้ปรับตาม meta ที่เปลี่ยนกลางทาง (SPA เปลี่ยน route โดยไม่โหลดหน้าใหม่) อย่างสม่ำเสมอ และ `layout.tsx` ล็อก `initialScale: 1, userScalable: false` อยู่ — ผลลัพธ์ต่างกันตามเบราว์เซอร์ ทดสอบยาก
- ย่อ **ทุกอย่าง** รวมตัวอักษรและปุ่ม → ผิดกฎ ≥ 20px / ปุ่ม ≥ 48px ใน `AGENT.md` โดยคุมไม่ได้

### ทางเลือก B — กล่องขนาดตายตัว (เช่น 390 × 760) แล้ว `transform: scale()` หรือ `zoom` ทั้งกล่อง ⚠️ ทางลัด ไม่แนะนำเป็นทางหลัก

ห่อพื้นที่เล่นด้วยกล่องขนาดคงที่แล้วย่อทั้งกล่องด้วย CSS — ง่าย ได้ผลทันทีกับทุกเกม แต่:
- `ResizeObserver` / `clientWidth` คืนขนาด **ก่อน** transform ส่วน `getBoundingClientRect` คืนขนาด **หลัง** transform — โค้ดวัดขนาดและแปลงจุดแตะของ G13/G18/G19/G20 ใช้ทั้งสองแบบปนกัน ต้องไล่แก้ทุกจุดอยู่ดี
- canvas ที่ถูกย่อ/ขยายด้วย CSS จะเบลอ ถ้าไม่ปรับ buffer ตาม
- ย่อข้อความและปุ่มลงเท่ากัน → ข้อความต่ำกว่า 18px และปุ่มต่ำกว่า 48px บนจอเล็ก (ผิดกฎ accessibility)
- พื้นที่ที่เหลือรอบกล่องกลายเป็นขอบว่าง (letterbox) แทนที่จะขยายฉากออก

### ทางเลือก C — design resolution + ตัวคูณสเกลร่วม ที่แต่ละเกมนำไปใช้เอง ✅ แนะนำ

1. **แกนกลางร่วมหนึ่งชุด** วัดพื้นที่เล่นจริง → คำนวณ `s` → ให้ทั้ง canvas และ CSS ใช้ค่าเดียวกัน
2. **เกม canvas** (G13, G20) ใช้ `s` ตอนวาดและตอนแปลงจุดแตะ (แบบที่ G20 ทำอยู่แล้ว) — ฉากหลังขยายออกเต็มจอได้ ไม่มีขอบว่าง
3. **ส่วน DOM** (HUD, กระดาน G18/G19, ข้อความ) ใช้ `s` ผ่านตัวแปร CSS `--gp-s` / `--gp-t` ที่มีอยู่แล้ว เปลี่ยนจากค่าขั้นบันได (1 / 0.82 / 0.68) เป็นค่าต่อเนื่อง — utility `gp-*` เดิมมี floor ข้อความ 18px และ `gp-tap-min-h-*` มี floor 48px อยู่แล้ว จึงคุมกฎ accessibility ได้ในจุดเดียว

ข้อดี: ปรับทีละเกมได้ (ไม่ต้อง big-bang), กฎ accessibility ยังบังคับได้, ไม่พึ่งพฤติกรรมเฉพาะของ LINE/Safari, G20 ใช้แบบนี้อยู่แล้วจึงมีของจริงให้เทียบ

## 6. การออกแบบระบบที่แนะนำ (ทางเลือก C)

### 6.1 สูตรสเกล

```
พื้นที่เล่น (w, h)   = ขนาดกล่องที่เกมวาดได้จริง (หลังหัก HUD) — วัดด้วย ResizeObserver
ขนาดอ้างอิง (W0, H0) = พื้นที่เล่นบนเครื่องที่ทีมเห็นว่า "พอดี" (กำหนดต่อเกม)

s = clamp( min(w / W0, h / H0),  S_MIN,  S_MAX )
```

- **`min(...)`** — ใช้ด้านที่ขาดมากกว่า จึงไม่ล้นทั้งแนวกว้างและแนวสูง (เหมือน `fitStage` ของ G20)
- **`S_MAX = 1`** — ไม่ขยายเกินขนาดที่ออกแบบ (แท็บเล็ต/จอใหญ่เหมือนเดิม) ถ้าภายหลังอยากให้แท็บเล็ตใหญ่ขึ้นค่อยเพิ่มเป็น ~1.15
- **`S_MIN ≈ 0.6`** — กันไม่ให้เล็กจนแตะไม่ได้/มองไม่เห็นบนจอเล็กผิดปกติ ถ้าต่ำกว่านี้ให้ใช้วิธี scroll ตามกฎ "ทุกหน้าต้อง scroll ได้" (สำหรับส่วน DOM) หรือยอมให้ฉากแน่นขึ้น (สำหรับ canvas)
- **ขนาดอ้างอิงต่อเกม:** ให้เปิด overlay จากข้อ [S0](#s0-วัดผลบนเครื่องจริงก่อน-ทำก่อนทุกข้อ) บนตัวจำลองตัวที่ทีมใช้จูนเกมจนพอใจ (เช่น iPhone 12 Pro 390 × 844) แล้วจดขนาดพื้นที่เล่นที่วัดได้มาเป็น `W0, H0` — แบบนี้ **หน้าตาบนตัวจำลองเดิมจะเหมือนเดิมทุก pixel** (`s = 1`) และเครื่องที่เล็กกว่าจะย่อลงตามสัดส่วน

ตัวอย่าง G13 ถ้าพื้นที่เล่นอ้างอิง = 390 × 730 (ตัวเลขสมมติ ต้องวัดจริง):

| เครื่อง | พื้นที่เล่น (ประมาณ) | `s` | กรวยกว้าง |
|---|---|---|---|
| ตัวจำลอง 390 × 844 | 390 × 730 | 1.00 | 127 px (เหมือนเดิม) |
| median 384 × 666 | 384 × 552 | 0.76 | 96 px |
| LINE Android 360 × 612 | 360 × 498 | 0.68 | 86 px |
| 320 × 535 | 320 × 421 | 0.60 (ชน `S_MIN`) | 76 px |

### 6.2 ข้อห้ามเรื่อง accessibility (ต้องคงไว้หลังย่อ)

| สิ่งที่ย่อ | กฎ | วิธีคุม |
|---|---|---|
| ข้อความ DOM | ≥ 20px ปกติ, จอเล็กยอม ≥ 18px | ใช้ `gp-text-*` (มี `max(18px, …)` ในตัว) ห้ามคูณ `s` ลงขนาดตัวอักษรเอง |
| ข้อความบน canvas (เช่น `+1` ของ G13 `POPUP_FONT_PX = 24`) | เหมือนกัน | `Math.max(20, 24 * s)` — ไม่ย่อต่ำกว่า 20 |
| ปุ่ม/จุดแตะ | ≥ 48 × 48 px | `gp-tap-min-h-*` หรือ `min-h-[48px]`; ส่วนลากของ G13 (กรวย) ใช้พื้นที่ hit ที่ใหญ่อยู่แล้ว (`max(120, width × 0.3)`) ไม่ต้องย่อตาม |
| เวลา/ความเร็ว | ห้ามเพิ่มแรงกดดัน | ความเร็วร่วงของ G13 อิงความสูงอยู่แล้ว (`height × 0.245`) — เวลาที่ใช้ร่วงเท่าเดิมทุกจอ ไม่ต้องแก้ |

### 6.3 ไฟล์ใหม่

**`src/lib/gameViewport.ts`** — ฟังก์ชันบริสุทธิ์ (ไม่มี DOM) ให้ unit test ได้:

```ts
export type StageFit = { w: number; h: number; dpr: number; s: number; ox: number; oy: number };

/** ตัวคูณสเกลจากพื้นที่เล่นจริงเทียบขนาดอ้างอิง (ข้อ 6.1) */
export function stageScale(w: number, h: number, ref: { w: number; h: number }, min = 0.6, max = 1): number;

/** แบบ G20: วางเวทีขนาด ref ในพื้นที่ (w, h) — ชิดล่าง กึ่งกลางแนวนอน; ส่วนเกินให้ฉากขยายออก */
export function fitStage(w: number, h: number, ref: { w: number; h: number }): { s: number; ox: number; oy: number };

/** จุดบนจอ (clientX/Y เทียบมุมซ้ายบนของ canvas) → หน่วยเวที */
export function toStage(x: number, y: number, fit: Pick<StageFit, "s" | "ox" | "oy">): { x: number; y: number };
```

**`src/lib/useGameStage.ts`** — hook ที่ห่อ `ResizeObserver` (และ `visualViewport` resize สำหรับ iOS ที่แถบ URL ยุบ/ขยาย):

```ts
const { fit, ref } = useGameStage({ ref: { w: 390, h: 730 }, mode: "scale" /* หรือ "fit" แบบ G20 */ });
// ref       → ใส่ที่กล่องพื้นที่เล่น
// fit       → { w, h, dpr, s, ox, oy } — เก็บใน ref ด้วยเพื่อให้ game loop อ่านได้โดยไม่ re-render
// side effect: ตั้ง style --gp-s / --gp-t บนกล่อง root ของเกม (ข้อ S4)
```

**`src/tests/unit/gameViewport.test.ts`** — ทดสอบสูตรด้วยขนาดจาก log จริง (320×421, 360×498, 390×730 ฯลฯ), ค่า clamp, และ `toStage(fitStage(...))` กลับไปกลับมาได้ตรง

### S3 G13 ย่อสไปรต์ตามสเกล (แก้อาการหลัก)

มี 2 วิธี — **แนะนำวิธี 1** เพราะแตะ physics/กล้อง/การลากน้อยกว่า

**วิธี 1 (แนะนำ): โลกยังเป็น CSS px แต่ขนาดสไปรต์คูณ `world.unit = s`**
- เพิ่ม `unit` ใน `GameWorld` (ตั้งใน `resize()` บรรทัด 1282 จาก `stageScale(...)`)
- เปลี่ยนค่าคงที่ขนาด (บรรทัด 111–130) จาก `const` เป็นค่าที่คูณ `world.unit` ตอนใช้: `SCOOP_RADIUS`, `SCOOP_STACK_STEP`, `CONE_SCOOP_OVERLAP`, `CONE_WIDTH`, `CONE_HEIGHT`, `MAX_VISIBLE_STACK_PX`, `RENDER_STACK_LIMIT_PX`, และ `- 10` ระยะกรวยจากขอบล่าง (บรรทัด 379)
  - ทางที่ปลอดภัยคือให้ค่าคงที่เดิมเป็น "ขนาดที่ s = 1" แล้วสร้าง helper `geometry(world)` คืนค่าที่คูณแล้ว — จุดที่อ้างถึงต้องเปลี่ยนจาก `CONE_WIDTH` เป็น `g.coneWidth` ทั้งหมด (ใช้ grep ตามชื่อค่าคงที่)
- ลูกที่ร่วง: `radius = min(SCOOP_RADIUS × unit, width × FALLING_RADIUS_WIDTH_RATIO)` (บรรทัด 545) — ระยะกันซ้อน `radius × 2.8` และ margin ปรับตามเอง
- ส่วนประกอบ tutorial: ลูกศรนำทาง (`GUIDE_*` บรรทัด 199–205), มือ 👆, `POPUP_RISE_PX` คูณ `unit`; ตัวอักษร `+1` ใช้ `max(20, POPUP_FONT_PX × unit)` (ข้อ 6.2)
- การลาก (`handlePointerMove` บรรทัด 1398): `halfCone` ใช้ความกว้างกรวยที่คูณแล้ว — hit area ของ `pointerdown` (บรรทัด 1376) **ไม่ต้องย่อ** (ยิ่งใหญ่ยิ่งง่ายสำหรับผู้สูงอายุ)
- `resize()` ที่ปรับตำแหน่งของที่กำลังร่วงตาม `scaleX/scaleY` อยู่แล้ว (บรรทัด 1305–1316) — เพิ่มให้คูณรัศมีของที่ร่วงตามอัตราส่วน `unit` ใหม่/เก่าด้วย (กรณีหมุนจอ/แถบ URL ยุบกลางเกม)
- **ไม่ต้องแก้:** ความเร็วร่วง (อิงความสูงอยู่แล้ว), คะแนน/ความยาก (นับจำนวนลูก ไม่ใช่ px), ระยะเวลาเกม

### S4 HUD / ส่วน DOM ย่อแบบต่อเนื่องแทนขั้นบันได

ตอนนี้ `.gp-compact` ใน [`globals.css:868-889`](../../src/app/globals.css) ย่อแบบ 3 ขั้นตาม media query (`--gp-s` = 1 / 0.82 / 0.68) — จอ 781 px สูงกับ 779 px ต่างกันทันที 18% และจอที่ "เตี้ยกว่า 780 นิดเดียว" ก็ย่อเท่ากับ 661 px

- ให้ `useGameStage` ตั้ง `style="--gp-s: <s>; --gp-t: <t>"` ตรงบน element root ของเกม (inline style ชนะ media query ของ class จึง**ไม่ต้องแก้ CSS เดิม** และเกมอื่น/หน้าอื่นที่ใช้ `.gp-compact` ไม่ได้รับผลกระทบ)
- `t` (ข้อความ) ย่อน้อยกว่า `s` เช่น `t = 1 − (1 − s) × 0.35` — floor 18px อยู่ใน `gp-text-*` แล้ว
- ใช้กับ root ตอนเล่นของ G13, G18, G19, G20, G20K → `GameStageHeader`, `Button3D`, ข้อความใต้กระดาน ย่อตามโดยอัตโนมัติเพราะใช้ `gp-*` อยู่แล้ว
- หน้าแนะนำเกม (`GameIntro`) ไม่ต้องเปลี่ยน — scroll ได้อยู่แล้ว และใช้ร่วมกับเกมเรียนรู้
- อัปเดตคอมเมนต์ใน `globals.css` ว่าเกมสนุกตั้งค่าเองแบบต่อเนื่อง

### S5 G19 วัดกระดานจากพื้นที่จริงแทน `56dvh`

- แทน `maxWidth: min(352px, 56dvh)` (บรรทัด 1112) ด้วยการวัดพื้นที่ที่เหลือจริงแบบเดียวกับ G18 (`G18MemoryPads.tsx:195-219`) หรือใช้ `useGameStage` กับขนาดอ้างอิง 352 × 368 (ขนาดกระดานใน Figma)
- ภายในกระดานเป็น % + `cqw` อยู่แล้ว **ไม่ต้องแก้**
- ถ้า S0 พบว่า LINE Android ขยายตัวอักษร (`text_zoom > 1`): ผลไม้ของ G19 เป็นอีโมจิขนาด `cqw` ซึ่งอาจโดนขยายด้วย — ตัดสินใจหลังเห็นข้อมูล (ทางแก้: วาดอีโมจิเป็นรูปภาพ/SVG แทนตัวอักษร)

### S6 ทดสอบอัตโนมัติด้วย viewport จริง

- เพิ่ม project ใน [`playwright.config.ts`](../../playwright.config.ts) (ตอนนี้มีแค่ `Pixel 5`) ด้วยขนาดจาก [หัวข้อ 3](#3-หลักฐาน-ขนาดจอจริงจาก-log-ภาคสนาม): `320×535`, `360×612`, `384×666`, `390×669` (iPhone ใน LINE) + `390×844` (ฐานตัวจำลอง)
- test ใหม่ `src/tests/e2e/fun-game-viewport.spec.ts` — เปิดแต่ละเกมสนุกผ่าน `/lessons/<id>/game` เข้า phase เล่น แล้วตรวจ:
  - ไม่มี scroll แนวนอน, HUD + พื้นที่เล่นอยู่ในจอ
  - ทุกปุ่มที่กดได้ `boundingBox` ≥ 48 × 48
  - G13: อ่าน `s` จาก `data-stage-scale` (ให้ hook ใส่ attribute นี้ไว้) แล้วยืนยันว่าลดลงตามจอ
  - เก็บ screenshot ต่อขนาดจอ ไว้ให้ทีมดูเทียบ
- **ทดสอบมือบนเครื่องจริง (ต้องทำ ตัวจำลองไม่พอ):** Android ใน LINE ตั้ง "ขนาดการแสดงผล" สูงสุด + "ขนาดตัวอักษร" สูงสุด, iPhone ใน LINE ตั้ง Display Zoom = "ตัวอักษรใหญ่ขึ้น" — เทียบกับ `game_viewport` ที่ log ได้
