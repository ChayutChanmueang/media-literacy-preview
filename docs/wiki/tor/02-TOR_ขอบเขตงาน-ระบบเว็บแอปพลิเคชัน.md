# ขอบเขตงาน (Scope of Work) — ระบบเว็บแอปพลิเคชันเชิงโต้ตอบ รองรับมือถือและ Social Media Platform

> **สถานะเอกสาร:** ร่างแยก (Draft) สำหรับตรวจทานก่อนนำไปรวมเป็นหัวข้อ "ขอบเขตงาน" ในเอกสารหลัก [TOR_Interactive-เกม-ระบบ.md](./TOR_Interactive-เกม-ระบบ.md)
>
> เอกสารนี้ขยายรายละเอียดเชิงเทคนิคของขอบเขตงานเดิม (แพลตฟอร์ม / โครงสร้างเนื้อหา / เกม / การจัดเก็บข้อมูล / กรอบเวลา) ให้เป็น**กรอบงาน TOR สำหรับผู้พัฒนาระบบ**โดยเฉพาะ เนื้อหาอ้างอิงจากเอกสารออกแบบระบบที่ทีมสรุปไว้แล้ว ได้แก่ [System Design](../../software/01-system-design.md), [Architecture](../../software/02-architecture.md), [Data Schema](../../software/03-data-schema.md), [Application Flow](../../software/04-application-flow.md) และ [Game Design Document](../../gdd/00-concept.md) — จุดใดยังไม่สรุป (เช่น จำนวนเกม, งวดงาน) ให้คงไว้เป็น **[ระบุ]** ตามเอกสารหลัก

---

## 1. ภาพรวมและหลักการออกแบบระบบ

พัฒนา **เว็บแอปพลิเคชันเชิงโต้ตอบ (Interactive Web Application)** รูปแบบ Single Page Application (SPA) ที่ออกแบบตามหลัก **Mobile-First** โดยมีเป้าหมายให้ผู้สูงอายุและวิทยากรระดับชุมชนเข้าถึงผ่านลิงก์ที่ส่งต่อทาง**แพลตฟอร์มโซเชียลมีเดีย (Social Media Platform)** ได้ทันที โดยไม่ต้องติดตั้งแอปหรือสมัครสมาชิก (**ไม่มีระบบ login**)

หลักการสำคัญที่ผู้พัฒนาต้องยึดถือตลอดการพัฒนา:

1. **Social Media-first, No-login** — ทุกเส้นทางการใช้งานต้องเปิดได้จากลิงก์เดียว ทำงานได้สมบูรณ์ภายในเบราว์เซอร์ในแอปโซเชียลมีเดีย (In-App Browser/WebView) โดยไม่ต้องออกไปเปิดเบราว์เซอร์อื่นก่อน
2. **Mobile-first, Low-end Device Ready** — ออกแบบและทดสอบบนมือถือ Android ราคาประหยัด/รุ่นเก่า และเครือข่าย 3G/4G ในพื้นที่ห่างไกลเป็นหลัก ไม่ใช่ desktop
3. **Accessibility for Elders (ข้อบังคับ)** — ตัวอักษรใหญ่ ปุ่มกดง่าย คอนทราสต์สูง เสียงอ่านประกอบ ไม่มีเมนูซับซ้อน (รายละเอียดหมวด 5)
4. **Privacy by Design (PDPA)** — ไม่เก็บข้อมูลระบุตัวตน เก็บเฉพาะข้อมูลจำเป็นต่อการประเมินผลโครงการ (รายละเอียดหมวด 6)

## 2. สถาปัตยกรรมและเทคโนโลยี (Technology Stack)

| ส่วนประกอบ | คุณสมบัติที่ต้องมี (Capability Requirement) | เหตุผล/ข้อกำหนด |
|---|---|---|
| ส่วนหน้าเว็บแอปพลิเคชัน (Frontend) | พัฒนาเป็นเว็บแอปพลิเคชันหน้าเดียว (Single Page Application) ขนาดไฟล์เบา รองรับการทำงานแบบ Progressive Web App เพื่อให้ติดตั้งเสริมได้ | โหลดเร็วบนเน็ตช้า รองรับอุปกรณ์มือถือเป็นหลัก (mobile-first) |
| การแสดงผลวิดีโอ | ระบบฝังวิดีโอ (embed) จากแพลตฟอร์มวิดีโอออนไลน์ รองรับวิดีโอแนวตั้ง 9:16 และมีกลไกตรวจจับสถานะ "ดูจบ" ผ่านช่องทางที่ผู้ให้บริการวิดีโอรองรับ | ใช้คลิปที่โครงการผลิตไว้แล้ว โดยไม่ต้องพัฒนาระบบสตรีมมิ่งวิดีโอเอง |
| เอนจินเกม (Game Engine) | ใช้เทคโนโลยีเว็บมาตรฐานสำหรับเกมทั่วไป และเลือกใช้เทคโนโลยีสำหรับกราฟิก/ภาพเคลื่อนไหวขั้นสูง (canvas) เฉพาะเกมที่จำเป็นต้องใช้จริง | ลดขนาดไฟล์โหลดรวม เลือกความซับซ้อนให้เหมาะกับแต่ละเกม |
| ระบบฐานข้อมูลและประมวลผลฝั่งเซิร์ฟเวอร์ (Backend / Data) | ระบบฐานข้อมูลที่รองรับการบันทึกประวัติการเข้าใช้งานแบบไม่ระบุตัวตน (ความคืบหน้าการเรียน, บันทึกกิจกรรมการใช้งาน) พร้อมความสามารถประมวลผลเบาฝั่งเซิร์ฟเวอร์ (เช่น แปลงข้อมูลตำแหน่งจาก IP) | เก็บข้อมูลอายุ/ตำแหน่ง/ความคืบหน้าเพื่อประเมินผลโครงการ โดยไม่ต้องดูแลเซิร์ฟเวอร์เอง |
| การระบุตำแหน่งจาก IP (Geolocation) | ระบบแปลงตำแหน่งจาก IP เป็นข้อมูลพื้นที่แบบหยาบ (จังหวัด/อำเภอ) ตั้งแต่ชั้นเครือข่ายก่อนถึงตัวแอปพลิเคชัน โดยไม่เก็บหรือส่งต่อ IP ดิบเข้าสู่ระบบ | สอดคล้องกับหลัก PDPA by-design ลดความเสี่ยงจากการเก็บข้อมูลระบุตัวตน |
| การให้บริการเว็บ (Hosting) | ระบบโฮสติ้งที่มีเครือข่ายกระจายพื้นที่ (CDN) ครอบคลุมกว้าง รองรับการโหลดหน้าเว็บเร็วแม้บนเครือข่ายมือถือความเร็วต่ำ และให้ลิงก์เดียวสำหรับแชร์ผ่านโซเชียลมีเดียได้ทันที | โหลดหน้าแรกสำเร็จภายใน 3 วินาทีบนเครือข่าย 3G |
| การติดตั้งใช้งาน (Installability) | ความสามารถติดตั้งเสริมแบบ Progressive Web App | เป็น **bonus** สำหรับผู้ใช้ที่กลับมาใช้ซ้ำ (เช่น วิทยากรชุมชน) ไม่ใช่เส้นทางหลัก เพราะเบราว์เซอร์ในแอปโซเชียลมีเดียส่วนใหญ่ไม่รองรับ install prompt โดยตรง |

> [ระบุ] — ตารางนี้จงใจเขียนแบบไม่ผูกกับผลิตภัณฑ์/ผู้ให้บริการรายใดรายหนึ่ง เพื่อเปิดกว้างให้ผู้รับจ้างเสนอเทคโนโลยีที่ตอบโจทย์คุณสมบัติและข้อกำหนดสมรรถนะ (Performance/NFR ในหมวด 7) ได้เอง ทั้งนี้ทีมพัฒนาภายในมีสถาปัตยกรรมอ้างอิงที่ยืนยันไว้แล้วใน System Design ผู้ว่าจ้างสามารถขอดูรายละเอียดทางเทคนิคเพิ่มเติมประกอบการพิจารณาผู้รับจ้างได้หากต้องการ

## 3. โครงสร้างฟังก์ชันของระบบ (Functional Modules)

ผู้รับจ้างต้องพัฒนาโมดูลต่อไปนี้ให้ครบถ้วน:

### 3.1 หน้าแรกต้อนรับและขอความยินยอม (Landing & Consent Module)
- หน้าแรกต้อนรับ + ปุ่มเข้าเรียน (สาธารณะ ไม่มี guard)
- หน้าขอความยินยอมเก็บข้อมูล (PDPA) ด้วยภาษาที่เข้าใจง่าย พร้อมปุ่มเลือกช่วงอายุ และยืนยัน/แก้ไขจังหวัด-อำเภอ-ตำบล (ตั้งต้นจาก IP geolocation)
- สร้าง anonymous session id แบบไม่มี login เก็บแบบ **Hybrid Persistence** (localStorage + Cookie, Max-Age 1 ปี, `SameSite=Lax`) เพื่อกันข้อมูลหายเมื่อเบราว์เซอร์ในแอปโซเชียลมีเดีย (In-App WebView) ล้างแคช

### 3.2 ตัวเลือกบทเรียนและระบบจัดลำดับการเรียน (Lesson Selector & Sequence Engine)
- หน้าเลือกบทเรียนแบบ Dashboard แสดงเส้นทางและดาวความคืบหน้า
- อ่านโครงสร้างบทเรียนจาก config/content file (ลำดับ: คลิป → เกม → บทถัดไป)
- รองรับ **Deep Link** เข้าตรงบทเรียน (`/lessons/:id/...`) สำหรับแชร์ผ่านแพลตฟอร์มโซเชียลมีเดีย พร้อมพารามิเตอร์พื้นที่ (เช่น `?ref=facilitator&prov=ChiangMai`)
- Router Guard: บังคับลำดับการเรียน (ต้องได้ดาวบทก่อนหน้าก่อนปลดล็อกบทถัดไป) และบังคับดูวิดีโอจบก่อนเข้าเกม

### 3.3 ตัวเล่นวิดีโอ (Video Player Module)
- ฝังวิดีโอ YouTube แนวตั้ง (9:16) ผ่าน YouTube IFrame API เพื่อดักจับสถานะเริ่มดู/ดูจบ
- Fallback ปุ่ม "เปิดใน YouTube" กรณี embed เล่นไม่ได้ในเบราว์เซอร์/อุปกรณ์บางรุ่น

### 3.4 โมดูลเกม (Game Module)
- โครงสร้างร่วม `GameShell` (โจทย์ทีละข้อ, เฉลยพร้อมคำอธิบาย, progress dots, ปุ่มเสียงอ่าน) + game type plugin ต่อรูปแบบเกม (quiz / tap-to-spot / swipe / scenario / action)
- ข้อมูลโจทย์แยกเป็น content file (JSON) ไม่ผูกกับโค้ด เพื่อให้ทีมเนื้อหาแก้ไข/เพิ่มโจทย์ได้โดยไม่ต้อง build ระบบใหม่
- ทุกเกมต้องไม่มีเงื่อนไข "แพ้" ที่สร้างความอาย — ตอบผิดต้องมีเฉลยพร้อมเหตุผลเสมอ
- เนื้อหาที่สร้างจาก AI ในเกม (ภาพ/เสียง) ต้องมี field เปิดเผยแหล่งที่มา (`ai_disclosure`) แสดง**หลัง**เฉลยเสมอ

> รายชื่อเกมย่อยที่ทีมออกแบบไว้ (G1–G7) และรายละเอียดกลไกอยู่ใน [Core Mechanics](../../gdd/01-mechanics.md) — จำนวนเกมจริงที่จะพัฒนาให้ยึดตามงบประมาณตามที่ระบุในเอกสารหลัก (ยังเป็น **[ระบุ]**)

### 3.5 ความคืบหน้าและรางวัล (Progress & Reward Module)
- ระบบดาวต่อบทเรียน แสดงผลในหน้าเลือกบทเรียน
- หน้าใบประกาศเมื่อเรียนครบทุกบท (ใส่ชื่อเล่นได้ / render เป็นภาพ / บันทึกลงเครื่อง / แชร์เข้าแพลตฟอร์มโซเชียลมีเดีย)
- ไม่มีระบบคะแนนแข่งขันหรือจับเวลาในโหมดผู้สูงอายุ (ลดความกดดัน)

### 3.6 โหมดวิทยากร (Facilitator Mode)
- เส้นทางแยก (`/facilitator`, `/facilitator/:id`) ไม่ต้องมีระบบสิทธิ์ซับซ้อนในเฟสแรก
- Layout สำหรับจอโปรเจกเตอร์/desktop (ไม่ใช่ mobile layout): วิดีโอขนาดใหญ่ + สคริปต์พูดประกอบต่อบท + ปุ่มควบคุมถัดไป/ย้อนกลับ
- ไม่มี Guard จำกัดลำดับบท — วิทยากรข้ามไปสอนบทใดก่อนก็ได้

### 3.7 การจัดเก็บและวิเคราะห์ข้อมูล (Data Collection & Analytics)
- Session Sync ระหว่าง localStorage และ Cookie อัตโนมัติ
- IP Geolocation Parser — ไม่เก็บ Raw IP Address แต่แปลงเป็นข้อมูลระบุตำแหน่งในระดับจังหวัดและตำบล เพื่อใช้วัดผลการเผยแพร่สื่อในพื้นที่งานวิจัย
- Event Logging (Async, ไม่บล็อก UI) บันทึกการกดปุ่ม/พฤติกรรมสำคัญลง `action_logs`
- แดชบอร์ดสรุปผล: จำนวนผู้เรียนแยกพื้นที่/ช่วงอายุ, อัตราการเรียนจบต่อบท (funnel), โจทย์ที่ตอบผิดมากที่สุด, ความถี่การใช้ฟังก์ชันต่างๆ

รายละเอียดตารางข้อมูล (`sessions`, `lesson_progress`, `action_logs`, `game_answers`) อยู่ใน [Data Schema](../../software/03-data-schema.md)

## 4. ข้อกำหนดเฉพาะสำหรับการรองรับมือถือและ Social Media Platform

หัวข้อนี้เป็นข้อกำหนดบังคับ (ไม่ใช่ทางเลือก) เนื่องจากกลุ่มเป้าหมายหลักเข้าถึงระบบผ่านมือถือและลิงก์ที่แชร์ผ่านแพลตฟอร์มโซเชียลมีเดียเกือบทั้งหมด:

1. **ทดสอบบน In-App Browser ของแพลตฟอร์มโซเชียลมีเดียจริง เป็นสภาพแวดล้อมหลัก** — ไม่ใช่ desktop Chrome/Safari เพียงอย่างเดียว ต้องยืนยันว่าทุกฟีเจอร์ (วิดีโอ, เกม, แชร์, บันทึกความคืบหน้า) ทำงานได้ปกติภายใน In-App Browser/WebView ของแพลตฟอร์มที่กลุ่มเป้าหมายใช้งานจริง (เช่น LINE)
2. **Deep Link / การแชร์ผ่านโซเชียลมีเดีย** — ทุกบทเรียนและหน้าใบประกาศต้องมีลิงก์ตรงที่แชร์เข้ากลุ่ม/แชทในแพลตฟอร์มโซเชียลมีเดียได้ทันที (เช่น LINE) และเปิดแล้วพาผู้ใช้ไปหน้าปลายทางถูกต้อง (ข้ามหน้าเลือกบทเรียนได้หากมาจากลิงก์เฉพาะ)
3. **กันข้อมูลหายจาก WebView ล้างแคช** — ใช้ Hybrid Persistence (localStorage + Cookie อายุ 1 ปี) พร้อม fallback เป็นพารามิเตอร์ในลิงก์ (เช่น `?prov=ChiangMai`) กรณีอุปกรณ์ล้างข้อมูลทั้งหมด
4. **รองรับอุปกรณ์ปลายทางที่หลากหลาย** — มือถือ Android ราคาประหยัด/รุ่นเก่าเป็นอุปกรณ์อ้างอิงหลัก ไม่ใช่ iPhone/เรือธงรุ่นใหม่
5. **ประสิทธิภาพบนเน็ตช้า** — First load < 3 วินาทีบน 3G, ขนาด asset รวมต่อหน้า < 1MB, โหลดภาพ/เสียงแบบ progressive
6. **แนวตั้งเสมอ (Portrait-first)** — วิดีโอและหน้าจอเกมทุกหน้าออกแบบสำหรับถือมือถือแนวตั้งมือเดียว ไม่ใช่ landscape
7. **ปุ่มกด/พื้นที่แตะ ≥ 48×48px** เว้นระยะห่างชัดเจน เหมาะกับนิ้วผู้สูงอายุ ไม่ใช่ปุ่มขนาด desktop
8. **ไม่บังคับติดตั้งแอปหรือ PWA** — ผู้ใช้ต้องใช้งานได้ครบทุกฟีเจอร์จากการแตะลิงก์เพียงครั้งเดียว การติดตั้ง PWA เป็นเพียงตัวเลือกเสริม
9. **Offline-tolerant ระดับพื้นฐาน** — ไม่บังคับใช้งาน offline เต็มรูปแบบในเฟสแรก แต่เกมต้องเล่นต่อได้แม้ sync ข้อมูลไป backend ล้มเหลวชั่วคราว (คิวข้อมูลผ่าน service worker แล้วส่งซ้ำภายหลัง)

## 5. ข้อกำหนดการเข้าถึงสำหรับผู้สูงอายุ (Accessibility Requirements)

ข้อกำหนดบังคับด้าน UI/UX ที่ผู้พัฒนาต้องนำไปปฏิบัติในทุกหน้าจอ:

| ด้าน | ข้อกำหนด |
|---|---|
| ขนาดตัวอักษร | เนื้อหาหลัก ≥ 20px, ปุ่ม ≥ 22px และมีปุ่มขยายตัวอักษรได้ |
| คอนทราสต์สี | อัตราส่วน ≥ 4.5:1 ทุกข้อความ (ตามมาตรฐาน WCAG AA) |
| พื้นที่แตะ | ปุ่ม/พื้นที่แตะ ≥ 48×48px เว้นระยะห่างกันชัดเจน |
| การสื่อความหมายด้วยสี | ห้ามใช้สีเป็นตัวสื่อความหมายเดียว (ถูก/ผิดต้องมีไอคอน ✓ ✗ กำกับเสมอ) |
| เสียงประกอบ | ทุกโจทย์/เฉลย (อย่างน้อยเกมกลุ่ม Must) ต้องมีเสียงอ่านประกอบ |
| ภาพเคลื่อนไหว | ช้า ชัดเจน ไม่กะพริบเร็ว ไม่มีการจับเวลาบังคับ |
| การนำทาง | เส้นทางเดียวเป็นเส้นตรง ปุ่ม "ถัดไป" ใหญ่ชัด ไม่มีเมนูซ้อน ไม่มี hamburger menu |
| ภาษา | ประโยคสั้น ภาษาพูด หลีกเลี่ยงศัพท์อังกฤษที่ไม่จำเป็น (ไทยเท่านั้นในเฟสแรก) |

## 6. ความปลอดภัยของข้อมูลและ PDPA

1. **Anonymity by Default** — ห้ามมีช่องกรอกชื่อจริง นามสกุลจริง เบอร์โทร หรือเลขประจำตัวใดๆ ในระบบ
2. **Consent-Based Location** — ต้องมีหน้าขอความยินยอมก่อนเก็บตำแหน่ง; ผู้ปฏิเสธต้องใช้งานแอปได้ครบทุกฟีเจอร์เช่นเดิม และระบบต้องบันทึกสถานะยินยอม/ไม่ยินยอมไว้
3. **ไม่เก็บ Raw IP** — แปลงเป็นจังหวัด/อำเภอที่ edge (Cloudflare) ก่อนเข้าระบบเสมอ ไม่มี IP ดิบไหลเข้าฐานข้อมูล
4. **Data Minimization** — เก็บเฉพาะช่วงอายุ (ไม่ใช่วันเกิด), ตำแหน่งระดับหยาบ (จังหวัด/ตำบล), ความคืบหน้าการเรียนแบบ anonymous, และ event log การใช้งาน
5. **Row Level Security (RLS)** — การเขียนข้อมูล progress/log ต้องจำกัดให้เฉพาะ session ID ปัจจุบันเขียนได้เท่านั้น ป้องกันการเข้าถึงข้อมูลผู้อื่น

## 7. ข้อกำหนดที่ไม่ใช่ฟังก์ชัน (Non-Functional Requirements) — สรุปรวม

| ด้าน | ข้อกำหนด |
|---|---|
| อุปกรณ์เป้าหมาย | Android ราคาประหยัด/รุ่นเก่า เปิดผ่าน In-App Browser ของแพลตฟอร์มโซเชียลมีเดีย (เช่น LINE) |
| ประสิทธิภาพ | First load < 3 วินาทีบน 3G; asset รวมต่อหน้า < 1MB |
| Offline | ไม่บังคับเต็มรูปแบบในเฟสแรก แต่เกมต้องเล่นต่อได้แม้ sync ล้มเหลว (queue ผ่าน service worker) |
| ความปลอดภัยข้อมูล | ไม่เก็บข้อมูลระบุตัวตน; ตำแหน่งเก็บระดับหยาบ |
| ภาษา | ไทยเท่านั้น (เฟสแรก) |
| การติดตั้ง | PWA เป็น bonus ไม่ใช่เส้นทางหลัก |

## 8. สิ่งที่ไม่รวมอยู่ในขอบเขตงาน (Out of Scope)

> [ระบุ] — รายการนี้เป็นข้อเสนอเบื้องต้นจากทีมเทคนิค เพื่อกันความเข้าใจผิดเรื่องขอบเขต ผู้ว่าจ้างควรตรวจทานและยืนยัน/แก้ไขก่อนใช้เป็นเอกสารทางการ

- แอปพลิเคชันมือถือแบบ Native (iOS/Android App Store) — ระบบเป็นเว็บแอปพลิเคชันเท่านั้น
- ระบบสมาชิก/login แบบเต็มรูปแบบ (ยึดหลัก anonymous session ไม่มี login ในเฟสแรก)
- การผลิต/ตัดต่อวิดีโอเนื้อหาชุด "รู้ทันสื่อ" (โครงการจัดทำไว้แล้วแยกต่างหาก) — ขอบเขตนี้ครอบคลุมเฉพาะการฝังและเล่นวิดีโอในระบบ
- การลงทะเบียนบัญชีทางการหรือแอปเสริมระดับแพลตฟอร์มใหม่ (เช่น LINE Official Account / LIFF App) — หากต้องการใช้ฟีเจอร์ขั้นสูงของแพลตฟอร์มโซเชียลมีเดียมากกว่า deep link ธรรมดา (เช่น LINE Login, LIFF SDK) ต้องระบุเพิ่มเป็นขอบเขตแยก
- การแปลเนื้อหาเป็นภาษาอื่นนอกจากภาษาไทย
- Offline mode แบบสมบูรณ์ (เล่นได้ทั้งระบบโดยไม่มีเน็ตตั้งแต่ต้น)

## 9. สิ่งที่ต้องส่งมอบ (Deliverables)

> [ระบุ] — ควรยืนยันรายการนี้ร่วมกับฝ่ายจัดซื้อจัดจ้างและผูกกับงวดงานในเอกสารหลัก

1. ซอร์สโค้ดระบบทั้งหมด (repository พร้อมประวัติ commit)
2. ระบบที่ deploy ใช้งานได้จริงบน production (Cloudflare Pages หรือเทียบเท่า) พร้อมโดเมน/ลิงก์ใช้งาน
3. ฐานข้อมูลและ Edge Functions ที่ตั้งค่าใช้งานได้จริง (Supabase หรือเทียบเท่า)
4. แดชบอร์ดสรุปผลข้อมูลสำหรับทีมประเมินโครงการ
5. คู่มือการใช้งานเบื้องต้นสำหรับวิทยากรชุมชน (Facilitator Mode)
6. เอกสารทางเทคนิคส่งมอบ (system design / data schema / deployment guide) สำหรับการดูแลต่อหลังส่งมอบ
